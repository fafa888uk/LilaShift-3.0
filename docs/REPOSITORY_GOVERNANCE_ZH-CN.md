## 2. P0：主线整理与发布安全

- [ ] 为现有 main 和已发布标签保留可追溯引用；不移动或覆盖已发布标签。
- [ ] 审查双方独有提交，形成保留、替代、冲突和待核实清单；以独立 PR 审核整合方案，不直接强推 main。
- [ ] 在主线确定后，使项目版本、README（各语言）、变更日志、SECURITY.md 和下载说明一致。
- [ ] 记录每个发布版本的确切源码提交、构建号、构建工具版本、产物摘要、CI 结果及已知限制。
- [ ] 发布说明不得使用“无风险”或将模拟器通过等同于真实设备验证；缺少证据时明确标为未验证。

## 3. P1：仓库权限与工作流

- [ ] 为 main 和未来正式开发主线设置分支规则：禁止强推和删除，要求 PR、通过适用的构建/测试/许可检查，并解决审核意见。单人维护时应避免把无法满足的审批条件设为必选。
- [ ] 为版本标签设置保护；发布由维护者明确批准。
- [ ] 盘点一次性 apply 工作流，确认不再使用后通过 PR 逐批移除；保留历史提交作为审计依据。
- [ ] 普通检查任务采用只读权限；需要写权限的维护或发布任务单独授权并审查。
- [ ] 固定 CI 使用的第三方工具版本；对依赖更新和工作流修改进行单独审查。
- [ ] 检查 PR 的实际目标分支与 CI 触发范围是否一致，不把未触发的检查记录为通过。

## 4. P1：用户安全、隐私与回归验证

- [ ] 对版本级别的测试证据建立独立记录；注明设备类别、OS build、源码提交及结果，不保存可识别个人的设备信息。
- [ ] 在离线测试夹具中检查备份完整性、恢复拒绝路径、输入校验和异常状态；不能凭模拟器结果声明实际设备安全。
- [ ] 对涉及系统数据的功能保留明确风险提示、用户确认、退出路径和可恢复性说明；没有可靠证据不得标为已验证。
- [ ] 诊断报告默认脱敏，公开问题不得包含序列号、账户信息、密钥或其他个人信息。
- [ ] 优先核实 PR #11 的恢复安全事项是否已包含在发布版本中；逐个复核旧草稿 PR，不批量合并。

## 5. P2：长期可维护性

- [ ] 建立模块边界及责任清单，分离界面、纯业务逻辑和持久化；避免把大规模重构与功能改动混在同一个 PR。
- [ ] 记录现有 lint 债务，先约束新增代码，再逐步偿还旧债；保留已通过的回归测试。
- [ ] 清理过时文档、分支和草稿 PR 前先确认是否仍被引用；记录关闭原因。

## 完成标准

每项完成需要对应 PR 或配置证据、执行结果以及未验证事项。没有合并或配置证据的任务仍为待办。不得把本提案视为已实施的仓库设置。
